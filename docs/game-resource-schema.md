This is the current first-release generic equipment/admission contract for [performance-classes.md](performance-classes.md). The native types are exported and consensus/SDK integration is in progress. Current-source compilation, native-origin fixture export, custody tests and new proof qualification are required before release. The frozen audio/environment proof predates this schema and does not qualify it.

Returnable equipment is retained in `GameSessionRecordV1.resources`, immediately after `item_stakes`. It is not a second authoritative ledger store. `JoinGameSessionV1.resources` is required immediately after `application_data`, including an explicit empty vector for stock racing. `terminal_at_height` replaces the settlement-only height and is populated by both legal cancellation and proof settlement. `GameSessionEventV1` includes resources and the terminal height after its item-stakes field.

The native resource file is `../iroha/crates/iroha_data_model/src/game_resources.rs`, exported through the model and generic game module. The browser codec and validators live in `javascript/iroha_js/src/noritoGameResourceCodecs.js` and `src/gameResources.js`, exposed through the existing game API. Their field order is exact:

| Type | Ordered fields |
| --- | --- |
| `GameResourceReturnPolicyV1` | Explicit wire discriminant `0`: `ReturnToOriginalOwnerAtTerminal`. There are no other variants. JSON is `{ "kind": "return_to_original_owner_at_terminal", "value": null }`. |
| `GameResourceReservationClauseV1` | `nft_id: NftId`, `expected_metadata_hash: Hash`, `role_id: Hash`, `policy: GameResourceReturnPolicyV1` |
| `GameResourceRequirementV1` | Same field types/order as a clause, in a distinct type: an adapter requirement supplies no wallet authority. |
| `GameResourceReservationRecordV1` | `slot: u8`, `nft_id: NftId`, `metadata_hash: Hash`, `role_id: Hash`, `policy`, `original_owner: AccountId`, `custody: AccountId`, `reserved_at_height: u64`, `released_at_height: Option<u64>` |
| `GameResourceReservationSetV1` | `version: u16` (exactly 1), `network_id: NetworkId`, `session_id: Hash`, `records: Vec<GameResourceReservationRecordV1>` |

`role_id` is an exact 32-byte native hash with native canonical marker/checksum rules, rather than free text or a role inferred from NFT metadata. Clause/requirement lists are strictly increasing by raw role bytes. Retained records are strictly increasing by `(permanent slot, raw role bytes)`. Validation rejects misplaced entries; it never sorts or removes duplicates from wallet authorizations.

Every admitted NFT must also roundtrip its displayed identifier through the native `NftId` parser to the exact same typed identity. Length limits alone are insufficient: native domain constructors permit dotted component values whose short display is ambiguous and whose JSON cannot roundtrip. Such identities are rejected before game custody; the game adapter does not redefine global domain parsing.

There are at most 4 resources per participant, 32 permanent participant slots and 128 retained resource records per session. A canonical NFT identifier is at most 512 UTF-8 bytes, each canonical account identifier at most 16 KiB, each encoded clause/requirement at most 1 KiB, and the complete encoded set at most 1 MiB. These are independent generic limits; the first class adapter must still require exactly its one reviewed kit. The account string bound prevents unbounded primitive parsing before the encoded set limit can be checked. Native JSON or binary input readers must impose framing/allocation limits **before** decoding a vector; the pure typed validator is not an allocation guard.

Within a set, each NFT and custody identity is unique, each slot has one original owner and each owner has one slot. A custody identity cannot also be an original owner. When the full roster is provided, custody cannot equal any participant, including one with no equipment. Reservation height is nonzero. All records are either unreleased or released at one common height at least as high as every reservation; there is no partial-release representation accepted by set validation. The record has no alternate recipient, deadline-unlock field, winner policy, burn flag or arbitrary purpose. Only the original owner may receive the return. These retained heights are audit fields, not mutable physics inputs.

Native pure helpers are `validate_resource_clauses_v1`, `validate_resource_requirements_v1`, `match_resource_requirements_v1`, and the set methods `validate` / `validate_for_owners`. The browser implements corresponding `validateGameResourceClausesV1`, `validateGameResourceRequirementsV1`, `matchGameResourceRequirementsV1` and `validateGameResourceReservationSetV1` through the generic game API. SDK validation returns canonical copies; the match function returns no value on an exact match and throws otherwise. Neither validation nor a compiled requirement transfers an NFT. `application_data`, wagers, fungible stakes and explicit typed resource authorization remain separate.

The current SDK codec uses the compact bare layout: struct fields have canonical minimal unsigned LEB128 byte lengths, vectors have a little-endian u64 element count and compact element lengths, and the closed unit enum has its explicit little-endian u32 discriminant. Primitive NFT/account/hash/integer serialization reuses the existing canonical SDK codecs. Public codec names cover the five independent types and the bounded `clauses` / `requirements` vectors. The decoder checks overall bytes, element counts, exact fields, unknown policy tags, dense data arrays, integer widths and canonical re-encoding. It accepts no guessed layout or alternate join instruction. Native fixture exports separately retain framed archives and exact schema identities for parity checking.

The first release has one join layout, one closed custody purpose enum (`Sale`, `GameWager`, `GameResource`) and one admission commitment. No old join decoder, purpose alias, optional-resource fallback or `roster-with-items` domain remains. Wallet equipment clauses must exactly match the compiled adapter requirements before admission or stake mutation. Stock racing accepts no equipment and one cosmetic byte; a future classed relation must constrain its own exact kit/catalog policy. Metadata cannot supply arbitrary physics parameters.

The immutable admission projection is defined in `iroha_data_model/src/game.rs`:

| Type | Ordered fields |
| --- | --- |
| `GameAdmissionParticipantV1` | `account`, `input_key`, `application_data` |
| `GameAdmissionWagerV1` | `slot`, `nft_id`, `metadata_hash` |
| `GameAdmissionResourceV1` | `slot`, `nft_id`, `metadata_hash`, `role_id`, `policy` |
| `GameAdmissionBodyV1` | `version: u16` (1), `participants`, `wagers`, `resources` |

The sole `game_roster_hash_v1(network, session_id, admission)` hashes the canonical tuple `(session_id, admission)` under the network-bound `roster` domain. Owners derive from permanent slots; NFT custody derives from network/session/purpose/NFT. Mutable forfeits, recipients, claim markers and reservation/release heights are excluded by explicit projection, without sorting or normalizing retained records. There are no duplicated custody/owner strings in proof admission. `GameAdmissionBodyV1::from_session` constructs this projection and `validate` rejects invalid geometry, duplicate accounts/Ed25519 keys, unordered or overlapping NFT authorizations, and excessive lengths.

In addition to the resource limits above, public admission bounds each encoded account controller at 32 KiB and each encoded NFT identifier at 1 KiB. These are independent of the 16 KiB/512-byte literal bounds: account encoding contains controller policy rather than a display string. Participant application data is at most 4 KiB and the entire encoded admission body at most 1 MiB. Stock racing imposes 2–8 participants, exactly one cosmetic byte per participant, at most one wager per slot, and no equipment. Native proof-size accounting reserves the encoded controller and NFT bounds plus all canonical framing; it does not measure only a small fixture body.

`RaceProverRequestV1` and `RaceProofPayloadV1` include required `admission` immediately after `manifest`. The native verifier validates the complete body and recomputes its commitment, in addition to the existing network/session/manifest/transcript/dispute/outcome bindings. A valid mathematical proof does not independently establish NFT ownership; that authority comes from authenticated ledger admission and finalized settlement inclusion. A worker only receives public data.

Native reservation preparation checks the complete projected admission and exact NFT ownership/metadata before mutation. Terminal movement uses one cumulative preflight for up to 160 NFTs: 32 wagers plus 128 returnable resources. Separate preflights could overwrite owner/domain reference decrements and are forbidden. Wagers follow the fixed winner/tie policy; equipment always returns to its original owner at the legal terminal height. A deadline or active forfeit cannot release equipment. Nonempty resources require a qualified profile even when XOR stake is zero.

Restore validation cross-checks canonical admission, immutable manifest/profile, terminal phase/height, exact original owners, derived custody, metadata and release recipients. Forward session records and inverse native custody records must match, including retained terminal records. State roots include the complete authoritative session and NFT custody stores. Generic transfers, burns, domain cascades and account mutation continue to respect shared custody guards.

Native fixture generation uses the explicit ignored exporter in `iroha_data_model/tests/game_v1_codec.rs`. It reads semantic seed values, parses actual native types and emits native canonical JSON, bare bytes, framed archives/schema identities and gameplay digests. It never treats JavaScript-generated bytes as native provenance. The current seed has 24 rows, including populated and empty admission bodies/commitments and required-resource join payloads. Unit enum JSON content is explicit null; u64 values must not pass through rounded JavaScript numbers.
