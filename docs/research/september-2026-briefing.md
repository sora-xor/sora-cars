**Recommendation: prioritize complete execution authentication, then reduce the cost of repeated state transitions, memory checks and commitments.** Keep native Rust and generic Iroha execution/game facilities, with racing expressed as a compiled application relation. The research supports several serious backend experiments; it does not yet select a replacement for the complete native prover. No external zkVM is required to apply these techniques. The next comparison must hold the compiled computation, accepted-input evidence, build configuration and final verification scope constant. Report complete proof bytes, total proving and verification time, peak memory, retained accumulator state and final-decider cost; an isolated component speedup is insufficient.

**Additional findings from this recheck**

The author WARP implementation makes the accumulation boundary concrete. Its inspected Goldilocks benchmark calls `prove` with an empty previous accumulator; it does not time repeated history updates, verification or the final `decide`. That decider rebuilds a Merkle tree, checks polynomial/relation evaluations and re-encodes the witness. Its Rust accumulation implementation also requires a `PrimeField`, so native Fp4 challenges need an explicit adaptation. These are read-only observations of the author repository's dynamic `main` on September 8, not a pinned release or reproduced benchmark. [Benchmark source](https://github.com/compsec-epfl/warp/blob/main/benches/warp_rs.rs), [implementation and decider](https://github.com/compsec-epfl/warp/blob/main/src/lib.rs).

Limber adds a direction missing from the earlier shortlist. Its late choice of prime is part of a different integer mod-PCS protocol, not a parameter adjustment to the present Goldilocks relation. This is a parameter-admission finding, not a protocol attack. The August paper and September repository use materially different benchmarks; neither measures our signed fixed-point simulation. [Limber, revised August 19](https://eprint.iacr.org/2026/1635).

**Security consequences for the first Iroha release**

- Bind the concrete emitted relation and expected execution statement before challenges. Fenzi's August 31 preprint, approved September 1, attacks certain generated-statement protocols and formalizes a mitigation under an underlying-security premise. Hashing generator code alone is insufficient in that setting. [Primary paper](https://eprint.iacr.org/2026/1838).
- Establish the full composition premises. The June 2 functional-commitment revision requires state-restoration security and state-restoration function binding. Ordinary binding alone is not its theorem. [CRYPTO 2026 paper](https://eprint.iacr.org/2025/902).
- Fix hash parameters and their joint derivation. August's Midpoint Reset constructs a full-round original-Poseidon collision with an adaptively selected MDS matrix after constants are fixed. It does not demonstrate a break of every Poseidon instance or our pinned Goldilocks/Poseidon2 instance. Profile registration must not allow arbitrary caller-selected matrices or weakened parameters. [Attack model](https://eprint.iacr.org/2026/1760).
- Review general attack techniques as well as matching examples. The August 15 subspace-restriction paper reports reduced-round KoalaBear experiments, but its gadget is described more generally. A different field or exponent alone does not dismiss it. Applying its constraint model to our exact Poseidon2 layers and sponge interface remains an open analysis; these experiments are not a demonstrated native sponge collision. [Primary preprint](https://eprint.iacr.org/2026/1692).
- Budget at least 128 bits for the complete accepted execution under an explicit adversary model. Field size, a library's target flag, or the security of one component is insufficient. Count algebraic/lookup errors, extraction, every opening, hashes, Fiat–Shamir and adaptive composition. Classical and quantum security claims need separate reductions. The [existing allocation analysis](crypto-2026-native-design-review.md) is an illustrative budget, not qualified parameters.

A subsequent [native hash-accounting review](2026-09-09-native-hash-accounting.md) finds that Iroha entity hashes use 255 variable output bits because one marker bit is fixed. Under an ideal model, generic collision work is on the order of 2^127.5, while independently fixed-target binding has a different bound. The review classifies state, prefix, snapshot and relation identities; it establishes no practical attack or complete proof-system failure. These roles must be accounted for explicitly before claiming at least 128 bits for the composition.

Post-quantum authentication remains a separate design layer. NIST's August 5 status lists finalized **ML-KEM, ML-DSA and SLH-DSA**, while Falcon and HQC standardization is ongoing. Hash-based execution proofs do not automatically migrate wallet signatures, race input keys, Connect key exchange or consensus certificates. [NIST status](https://csrc.nist.gov/projects/post-quantum-cryptography).

**Lemur**, revised September 2 and accepted at CCS 2026, is a new candidate for post-quantum synchronized multisignatures under Module-LWE/Module-SIS. Its headline sub-8 KB figure concerns aggregated one-time signatures; the abstract reports 380 KB for the complete million-signer multisignature. It requires synchronized signing and state management. Study it for future consensus authentication separately from execution proofs; these author benchmarks do not qualify a replacement for Iroha finality certificates. [Paper and status](https://eprint.iacr.org/2026/1161).

The inspected Lemur author artifact at `d2003964667bf553bb408a99525c1e86940ef9b9` ships a 1,024-signer profile. Its README distinguishes larger-size predictions/extrapolations and verification using accepting all-zero fixtures from distinct-signer end-to-end runs. Native adoption would first need realistic certificates, aggregation and crash-safe signing-state tests. [Pinned artifact and benchmark scope](https://github.com/lemur-sig/lemur/blob/d2003964667bf553bb408a99525c1e86940ef9b9/README.md).

Public replays need execution soundness, not hidden witnesses. Future games with private hands or hidden state can use the 2026 work on honest-verifier zero-knowledge IOPPs as a reference, but require their own noninteractive composition and privacy analysis. [Primary preprint](https://eprint.iacr.org/2026/391).

**Implementation order resulting from this study**

1. Complete native producer-to-verifier authentication of the selected ledger state and accepted gameplay history, including the association between the finalized record and computation proof. The [current finalized-history laboratory](../../world/native/NATIVE_FINALIZED_HISTORY.md) has synthetic ledger execution fixtures; it is not genuine producer interoperability or live settlement evidence.
2. Freeze one complete semantic benchmark: 2 and 8 cars; zero-motion closure and short ordered transitions; collisions, lookups, forfeits, terminal behavior and padding. Use identical accepted inputs and outputs for every backend. Record relation construction separately from proving and verification.
3. Compare authenticated lookup reductions and bounded-memory sumcheck; then compare FACS/WARP accumulation and the final decider. Measure whether gains survive complete state continuity, input authorization and all necessary commitments.
4. Compare WHIR/LiftWHIR, fragment-based commitments and ERA encoding within the complete winning construction. Keep binary and lattice alternatives separate until their whole workload costs and security arguments justify selection. Registration selects compiled profiles; it does not install arbitrary verifier code. First-release consensus has one canonical encoding per admitted version and no runtime compatibility fallback.
5. Qualify full-duration resources, composed security, supported CPU/accelerated targets, custody/settlement, four-validator operation and independent inclusion verification before live XOR/NFT stakes. A public-data proof worker may be untrusted; no worker's assertion replaces verification.
