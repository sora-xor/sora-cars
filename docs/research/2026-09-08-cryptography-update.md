**Cryptography advances for native Iroha games — September 8, 2026**

**Recommendation: compare a heterogeneous AIR backend with sparse sumcheck and authenticated matrix closing, preserve native Goldilocks/Fp4 initially, and qualify memory use across the entire prover.** WHIR and the new PIPFRI work deserve commitment-layer experiments. The latest security papers also require explicit generated-relation binding and jointly reviewed hash parameters. None of these publications qualifies our current prototype for staked settlement.

This updates the [September 7 survey](2026-09-cryptography-review.md) using primary papers, conference records, standards and pinned author code available by **September 8, 2026**. It interprets “crypto” as cryptography in the context of Iroha execution proofs. It covers relevant 2025 foundations and 2026 advances, including late-August publications and September revisions. It is a focused literature/design study, not a reproduction of external performance results or an exhaustive survey of cryptography. A publication date, a preprint revision and a repository observation are distinguished throughout.

The architecture remains **generic Iroha execution/game facilities with compiled application relations**. Published algorithms can inform native Rust implementations without adopting an external zkVM. This study does not change maintained Iroha code or deployment settings.

**The latest local measurements change the comparison.**

The earlier study measured an expanded bit-based circuit. We have since implemented detached range/ROM obligations, a closed native cryptographic lookup laboratory, and an immutable operand representation with an independent raw execution checker. The new [six-configuration census](../../output/qualification/street-operand-census/report.json) checks three actual native transitions per configuration, including first-terminal, state/action/final boundaries and padding. Numerical forfeits in those fixtures are test inputs; they are not authenticated ledger decisions.

The 8-bit three-tick raw run peaks at **800,669,696 bytes RSS**. Separately, an **unimplemented cost model** for a same-domain proof gives a best one-tick packed matrix of **10.125 GiB** among the tested eight-car configurations, before fixed polynomials, Merkle trees and scratch space. These numbers measure different things. There is no full-race proving-memory result. The [census interpretation](2026-09-08-memory-proofs-notes.md) records assumptions and exclusions; report SHA-256 is `b7600867dc748b7b64f51ff988fe44a089196b33a47964a236a94e5c4a152031`.

**Our inference:** changing a wide trace into a narrow sequence of scalar terms preserves semantics but can still create excessive commitment work. Keep that representation as a checked oracle and baseline. Compare proofs of compact operation relations and authenticated virtual reads before committing to its serialized layout.

**Advances with the strongest practical relevance**

| Work; available version/status | What it contributes | Implication for Iroha |
| --- | --- | --- |
| **WHIR** — EUROCRYPT 2025; **SWIRL** — March 13, 2026 manuscript | WHIR supports constrained polynomial openings. SWIRL combines heterogeneous AIRs, LogUp-GKR interactions and stacked WHIR commitments. [WHIR](https://eprint.iacr.org/2024/1586), [SWIRL](https://openvm.dev/swirl.pdf) | Compare separate arithmetic, range, geometry and state tables, including every interaction/opening reduction. The paper's conditional analysis still needs our parameters and composition. |
| **Twist/Shout** — CRYPTO 2026 publication; older ePrint revision remains dated February 2025 | Shout checks read-only accesses; Twist adds writes. One-hot addressing can reduce memory-checking costs. [Author publication record](https://www.microsoft.com/en-us/research/publication/twist-and-shout-faster-memory-checking-arguments-via-one-hot/) | Our immutable operand addresses primarily need read-only checking. Account for sparse commitments and address-polynomial evaluation; public wiring is not free verifier work. |
| **Logup\*** and its hash-based Twist/Shout adaptation — May/October 2025 manuscripts | Virtual evaluations and pushforward reductions can avoid explicit commitments to every expanded one-hot address. [Logup*](https://eprint.iacr.org/2025/946), [adaptation](https://www.powdr.org/papers/twist_shout_logup_star.pdf) | Compare this with the current read-copy model. Our larger operand table has different economics from tiny range tables; do not transfer small-table speedups. |
| **PIPFRI / DEPIPFRI** — USENIX Security, August 2026 | Partitioning a polynomial into fragments reduces encoding/opening work; the distributed variant adds worker accountability. [Final paper, §§4–6](https://www.usenix.org/system/files/usenixsecurity26-li-weihan.pdf) | Add a bounded native PCS comparison after relation selection. Its Rust/Goldilocks evaluation is relevant, but its benchmark uses **100-bit conjectured list-binding** parameters. It is not 128-bit full-game evidence. |
| **Scribe** — USENIX Security, August 2026 | Sequential disk-backed proving replaces large random-access memory. Its evaluation uses PST/BLS12-381 and a 750 MiB limit. [Final paper, §§9–10](https://www.usenix.org/system/files/usenixsecurity26-baweja.pdf) | Borrow the streaming approach; include disk, I/O, page-cache effects and repeated passes. Its pairing-based measurements do not predict our transparent prover's cost. |
| **Time-Space Trade-Offs for Sumcheck** — TCC 2025, revised February 25, 2026 | Formal trade-offs allow extra passes to reduce sumcheck memory. [Paper](https://eprint.iacr.org/2025/1473) | Evaluate memory across witness generation, sumcheck and commitments together. A low-memory inner protocol alone does not bound the whole process. |
| **GAPP** — CRYPTO 2026, full revision June 13 | Polynomial packing supports aggregation, tuple lookups and non-uniform computation. Its concrete bPCLB instantiation uses bilinear groups/KZG. [Full paper](https://eprint.iacr.org/2024/1685) | Useful design reference, with a different commitment model. A transparent adaptation would require additional construction and analysis. |

PIPFRI is particularly useful to add to the comparison because it studies the encoding-memory bottleneck directly. Its benchmark targets and its honest-worker baseline versus added accountability must remain explicit. Worker accountability also does not establish who authorized gameplay inputs; consensus must establish the accepted history. This is our application-level inference from its construction, not an additional claim by the authors.

**The implementation details behind a fast headline matter.** The inspected Spartan-WHIR repository is pinned to commit `f525cddea38bb605304d3a8e6394dda10ac64b4a`, dated September 1. Its documented 2,048-byte SHA-256 comparison targets **116 bits**. Its security code accepts targets only through **123 bits**, citing the digest's approximately 123.95-bit collision bound; its default assumption is `CapacityBound`. Larger extension fields alone do not remove either limitation. [Pinned security code](https://github.com/ethereum/spartan-whir/blob/f525cddea38bb605304d3a8e6394dda10ac64b4a/src/security.rs), [pinned benchmark documentation](https://github.com/ethereum/spartan-whir/blob/f525cddea38bb605304d3a8e6394dda10ac64b4a/README.md).

Our native quadratic sums are also not automatically rank-one constraints. A sparse backend comparison must count any added product witnesses, matrix commitments, matrix-closing proof and remaining range/ROM obligations. A verifier that scans the entire public matrix is useful as an oracle but may be unsuitable for validators. These are local design deductions; see the [backend assessment](2026-09-08-backend-notes.md).

**Security results that affect profile design now**

- **Bind the concrete generated relation before the first challenge.** Fenzi's August 31, 2026 preprint extends Fiat–Shamir attacks to certain generated-R1CS protocols and formalizes a mitigation using the generated statement. Hashing only generator/program code is insufficient in that setting. [Paper, especially §5.2](https://eprint.iacr.org/2026/1838). For Iroha, the proposed transcript must bind the actual compiled relation/parameters and externally expected execution statement, with a reviewed reduction for that exact protocol. This is not a demonstrated break of our implementation or a universal Fiat–Shamir fix.
- **Fix hash parameters jointly, including their derivation.** The August 21 **Midpoint Reset** preprint constructs a full-round original-Poseidon collision with an adaptively selected MDS matrix after constants are fixed. [Paper](https://eprint.iacr.org/2026/1760). Our read-only source inspection finds a different fixed Goldilocks/Poseidon2 instance; the attack does not demonstrate a collision in it. Nonetheless, registration must not accept caller-selected matrices or other weak hash parameters merely because isolated structural checks pass.
- **Use applicable proximity theorems.** Crites–Stewart's December 2025 revision disproves several original up-to-capacity Reed–Solomon conjectures. That invalidates those premises, not every FRI deployment. [Paper](https://eprint.iacr.org/2025/2046). A parameter planner must name the actual code family, theorem and composition losses. A benchmark's `security_bits` flag is not a qualification.
- **Analyze the exact commitment construction.** The July 22 revision of **The Billion Dollar Merkle Tree** proves binding/extractability for a particular prehashed Plonky3 design. [Paper](https://eprint.iacr.org/2026/089). Changing leaf framing, compression or digest widths requires matching the relevant theorem and assumptions; a primitive name alone does not provide the result.

The [security update](2026-09-08-proof-security-notes.md) records exact attack models and additional 2026 proximity/hash work. Internal review and passing malicious-witness tests are useful evidence, but they do not replace a cryptographic reduction or external review.

**Other advances worth tracking, with separate adoption decisions**

**PikkuFold**, first posted August 26 and revised August 29, proposes lattice-based folding with roughly 5.5 KB communication per step **excluding fresh-input commitments**. This is a very recent preprint with different assumptions, not a hash-based FRI replacement or a final proof of a whole race. It is relevant to future accumulation research after a complete native relation and final decider exist. [Paper record](https://eprint.iacr.org/2026/1809).

**Privacy:** February 2026 work on zero-knowledge IOPPs adds composable hiding reductions. Plain execution soundness and zero knowledge are different guarantees. Public replays make hiding optional for this game's initial proof; future private game relations need a separately qualified construction. [Primary preprint](https://eprint.iacr.org/2026/391).

**Post-quantum cryptography:** NIST's current standards include ML-KEM, ML-DSA and SLH-DSA; its August status still lists Falcon and HQC standards as forthcoming. May's additional-signature selection advances nine candidates, not nine new standards. [NIST status](https://csrc.nist.gov/projects/post-quantum-cryptography/post-quantum-cryptography-standardization/selected-algorithms), [May report](https://csrc.nist.gov/pubs/ir/8610/final). A transparent game proof does not migrate wallet signatures, input keys or consensus certificates automatically.

The August claim of an efficient quantum DCP/lattice algorithm must be read alongside the **September 1 revised refutation**, which also provides Lean code. These preprints do not establish that deployed lattice standards are broken. This study did not reproduce either analysis or check the Lean development. [Simon's claim and revision notes](https://eprint.iacr.org/2026/1591), [Gupte–Ragavan–Zhandry refutation](https://eprint.iacr.org/2026/1693).

**Concrete next experiments**

1. Freeze a complete, compiler-owned semantic workload and transcript manifest. Preserve all integer bounds, disabled branches, collision ordering, disconnected assertions, lookup occurrences, aliases, first-terminal rules and state/action boundaries. Include generated-relation identity, accepted-history binding and fixed hash provenance in the admission design.
2. Compare **heterogeneous AIR plus authenticated interactions** against **sparse sumcheck with authenticated matrix closing and virtual-read checks** on the same short complete executions. Keep Goldilocks/Fp4 initially. Compare WHIR and fragment-based PCS techniques within complete constructions; do not bolt an opening benchmark onto an incomplete relation.
3. Build and measure a genuinely bounded-memory prover for the winning candidate. Count native witness generation, fixed preprocessing, commitment/encoding passes, RAM, scratch disk, I/O, proof bytes and validator work. Bind every shard boundary and its order. Only then extend to 5,400-tick races and the 9,000-tick Tokyo exception.
4. Recompute the full security budget and qualify the implementation before admission. Specify the adversary model, challenge distributions, lookup/algebraic/proximity/Merkle events and Fiat–Shamir losses. The required **at least 128-bit** target must survive composition. Then complete generic consensus settlement, input/dispute authentication and finalized inclusion testing.

These experiments refine the active implementation goal; they do not replace it. Full Street cryptographic proving, composed security qualification, live XOR/NFT settlement and deployment remain open. The [source index](2026-09-08-source-index.json) records the main references, access cutoff and inspected version identities.
